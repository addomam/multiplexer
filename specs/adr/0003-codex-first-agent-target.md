# Target Codex local app-server first

## Decision and evidence

Use **Codex CLI 0.160.0 with an amux-owned local app-server and its ordinary native TUI** as the first implementation target for same-instance structured agent interaction. This is a design/target decision, **not** a claim that a production integration or the full acceptance contract has passed.

The [first private spike](../archive/spikes/SPIKE-native-agent-interaction.md) proved ordinary native TUI/API coexistence on the same real thread, genuine structured questions, API permission allow/deny, native permission approval and stale-request isolation. The [fencing follow-up](../archive/spikes/SPIKE-pty-control-fencing.md) narrowed the ownership seams with real running turns. This is stronger evidence for the required local route than the investigated alternatives.

OMP remains preferred in principle and its existing reporter/native support remains unchanged. The inspected OMP 18.8.7 native collaboration route uses a relay; RPC/rpc-ui alone does not prove coexistence with the ordinary native UI. No comparable complete local route was established for Claude Code. Do not add another provider or keep cycling candidates merely because an intentionally incomplete broker omitted required accounting.

The user explicitly requested deferring that native-buffer edge to final complete-broker validation if it remains unresolved. Preserve it as an acceptance check, not an immediate prerequisite to completing the design or a waiver of safe grant. Revisit first-target selection only if the actual integration cannot meet a mandatory requirement through supported interfaces; do not silently patch/fork the harness or substitute a shadow/headless-only agent.

## Process, PTY and identity boundary

An agent execution owns a private app-server/socket and a native Codex frontend on its amux PTY. The daemon supervises those resources; it does not attach to, modify or stop the user's existing global Codex daemon. The private API connection and that native frontend address one current thread. Multiple amux TUI attachments observe this same PTY/frontend; they do not each launch another Codex instance.

Ownership belongs to the live PTY, while agent identity additionally binds the managed app-server instance, current thread/session, turn and pending request/item where applicable. A selector, socket path or current human-readable label cannot substitute for these identities. A completed ownership transition cannot revive an old agent target or silently redirect an action to another turn/thread.

An existing persisted thread may be resumed through the experimentally proved remote-native path. For a fresh session, choose native-first creation on the owned server and discover that native-created thread through authoritative protocol events. Validate that launch path during implementation: the earlier API-first spike needed a real first turn before `resume` could find rollout history. Do not hide a fabricated bootstrap prompt/model turn, charge a setup turn, create a shadow conversation or read screen text to discover identity.

Detaching an amux viewer leaves the native PTY/frontend, backend and running turn intact. Explicit agent/process stop or PTY close is separate from turn cancellation and ownership operations, and must clean up all resources belonging to that execution. Unexpected frontend/backend exits expose degradation/unknown state, not success or silent recreation. Runtime restoration/reconnection automation remains out of scope.

The new structured-agent target is explicit; this ADR does not silently change stock Zsh, the existing `--omp` behavior or the default launch profile.

## Closed interaction contract

These are semantic operation names and required fields, not a generic provider-method passthrough or new ergonomic CLI commands. Implement a single explicit driver first; callers use amux identities and current ownership rather than invoking arbitrary harness methods outside admission/accounting.

- `AgentTarget`: live terminal ID, harness-instance ID and current thread/session ID.
- `PendingTarget`: that agent target plus turn ID, item ID and the exact provider request ID. Request IDs may be strings or integers as generated by the installed protocol; question IDs inside an answer are separate.
- Mutations carry current `ControlHandle`. Observations do not require taking control. Before dispatch, validate the live target, authority, applicable pending identity and operation shape together; then track the forwarded operation through its authoritative outcome.

| Semantic operation | Required caller intent | Codex binding and outcome boundary |
|---|---|---|
| Inspect / observe | Agent target and event cursor where applicable; no control required | Authoritative thread/request/lifecycle state and sequenced notifications. Distinguish active, awaiting input, completed/interrupted, unavailable and unknown. Observation never accepts an ownership offer. |
| Submit prompt | Target, control, text, explicit start or steer intent; steer also names the expected current turn | `turn/start` or `turn/steer` with `expectedTurnId`. Acceptance is not task success or whole-turn completion. A stale steer never falls back to starting another turn; an active-turn conflict never silently queues. |
| Answer question | Pending target, control, answers keyed by the pending question IDs | Respond to the real `item/tool/requestUserInput` request using its generated response shape. Validate offered question semantics and current identity; do not infer an answer from text or simulate keys. Known request resolution is separate from native-input queue settlement. |
| Decide permission | Pending target, control, explicit allow or deny for that request | Real approval response: e.g. command approval `accept` / `decline`, as runtime-proved. No inferred/session-wide approval. Other request kinds use their actual installed schema and explicit capability status, not a generic guessed payload or automatic acceptance. |
| Cancel turn | Agent target, control and exact turn ID | `turn/interrupt`. Its empty acknowledgement is not completed cancellation; observe interrupted completion and any later pending-request cleanup independently. Do not kill the process or cancel another turn when the target is stale. |

The driver retains a registry of authoritative pending requests and resolved/tombstoned identities. Old, duplicated, cancelled or resolved responses return explicit non-dispatched errors; they cannot be attached to a later question merely because labels or numeric IDs look similar. Lifecycle cleanup may follow turn completion, as observed in the first spike.

For free-text/multi-select questions and additional permission kinds, preserve the actual supported structured semantics. Do not claim those permutations have runtime proof from the single-select/command-approval probes. Mandatory real question and permission allow/deny support still gates first acceptance; unsupported or unknown encountered requests remain visible and cannot be auto-approved to unblock a turn.

## Integration with PTY control

Use the existing [control/claim/offer contract](../contracts/pty-control.md) for both native attachments and external controllers. Gating is daemon-local and checked again at dispatch; client-side assertions or a socket write alone are insufficient. Track existing calls rather than cancelling them on takeover. Force reports unresolved-call risk and preserves the turn; safe transfer waits for tracked settlement and reserved acceptance.

The [native UX contract](../tech-architecture/pty-control-native-ux.md) specifies request/owner notices, progress, cancel, force, idle keep-control and attachment scope. amux supplies observations and primitives; the external orchestrator chooses prompts, answers, permissions, reacquisition policy, scheduling and task acceptance. No new retry engine, agent planner, provider registry, relay or generic plugin infrastructure belongs in this cut.

## Acceptance boundaries

The two private experiments supply real evidence only for the recorded scenarios. Production first acceptance still needs the complete broker on actual amux, native ownership UI, authoritative interaction presentation, real question/permission operations, token-gated dispatch, one-shot controller recovery, multiple clients, safe/non-cancelling forced handoff, cancellation and externally requested reacquisition.

Native/API optimistic-answer presentation and queued-native-input coverage are tested under the completed ownership mechanism; the uncontrolled race and incomplete-broker negative control are not themselves evidence that the selected complete integration fails. Do not falsify presentation or advertise a passed safe transition if an actual unresolved outcome remains. No fixed sleep substitutes for settlement.

The approved Plan passed both independent reviewers and the user explicitly authorized Build. This does not reset the inherited exhausted review cap or authorize landing. The user subsequently authorized bounded real-harness checks with existing authentication and cheapest compatible non-sol models.

## Build observations

The concrete broker uses the pinned Unix WebSocket transport and the six closed `agent-*` operations. Initial control is bound to the requesting controller; current authority is rechecked at actual dispatch. Request IDs retain string/integer type and full session/turn/item identity. Retained calls and tombstones survive ownership changes. Request-only command/file decisions do not broaden into turn/session grants; unsupported provider permission kinds remain explicit.

Fresh native-first launch creates no setup model turn. Live metadata can be read before a rollout exists; `thread/resume` rejects that zero-turn state even with `excludeTurns`. Discovery therefore reads the native-created live identity. Upstream automatic listener attachment is best-effort, not runtime proof that every required event reaches this observer. An ephemeral native `thread_title` helper is not a replacement root; an unexpected ordinary root still invalidates the target.

Initial account checks exposed missing scoped observation despite global metadata/status events. The broker now explicitly resumes the same native-created root after the first requested turn materializes history, requesting `initialTurnsPage` and reconciling authoritative completion without reviving ended turns. Fresh zero-turn metadata still binds identity without a setup prompt. Late attachment cannot restore a degraded connection.

Separate exact live checks now pass native/API start/steer, a genuine native-originated Plan-mode question answered structurally, permission allow/deny with actual effects, and exact-turn interruption with process survival and owned stop cleanup. Evidence uses the supported paginated turn API; completed proposed-plan items are authoritative output, not user echo. These slice checks do not certify native winning-answer races or complete-broker acceptance.

`availableDecisions` describes native menu choices. The pinned response handler independently accepts request-only `decline`, even when that menu omits it, and maps `cancel` to interruption instead. amux uses `decline` for deny, never a session/policy grant or `cancel`; allow remains constrained by the offered request. This distinction was reproduced in a failing-before/passing-after regression and then exercised with real deny/no-file-effect/continued-turn proof.

The final complete-broker check reached its first safe offer and failed because application settlement remained unknown. It did not reach or pass all 32 scenarios, the stopped-native-buffer edge or winning-answer presentation. No timer, whole-turn finish or force-only path substitutes for that missing fence. See [integrated Build evidence](../verifications/e03-integration-build.md) for exact exercised boundaries and cleanup.

## User-authorized temporary acceptance deferral

After the failed complete-broker check and source-level diagnosis, the user chose to keep upstream Codex unmodified and explicitly accepted its temporary native fence and losing-answer presentation limitations. Complete-broker/all32 proof is deferred to future ACP integration, not retroactively passed. Existing native/API operations remain useful; unknown native input still blocks safe grant and force remains explicitly risky and non-cancelling.

This is an explicit amendment to the current delivery gate, not evidence that an ACP connector already exists or inherently solves native buffering. Before closing the original gap, that integration must prove the same generation-bound native application cut and authoritative answer presentation. No upstream patch, replacement UI or ACP implementation is included. See [accepted limitations](../security/EXCEPTIONS.md).
