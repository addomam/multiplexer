## Genuine ID seam (B-01)

`ExtensionUIContext.approve(prompt)` receives full/compact text and optional session/grants, **not toolCallId**. Do not manufacture an SDK ID, parse prompt text or read a latest-event variable. `ExtensionToolWrapper` instead awaits `tool_approval_requested` with genuine sessionId/toolName/toolCallId, then calls `requestApproval`, and eventually emits `tool_approval_resolved` for that same ID. Generic runner emit awaits registered handlers, but isolates their exceptions/timeouts and can continue. Therefore a naive observer or throwing handler alone is not a gate.

Register adapter-owned inline `tool_approval_requested` and `tool_approval_resolved` handlers via the supplied extension factory **before** enabling tools. Configure the same typed UI context in both setToolUIContext and initializeExtensions, once. Install the runtime error callback before requests can run; it must synchronously trip the gate on handler failure/timeout before the wrapper's awaited emit resumes. Initial profile permits no independent direct approve caller; one unregistered/missing identity path fails closed, never receives a guessed binding.

### Bounded serialized approval gate

State: one active record `{SDK-session,SDK-tool-call,tool-name,phase,ToolV1-request,responder}`, FIFO of at most63 waiting event records (64 total), <=64KiB encoded retained identity metadata, generation/closed bit and bounded terminal IDs. No prompt matching. This serializes **approval acquisition only**, not the whole agent turn and not amux authority. Read-only/autonomous non-approval work can continue.

1. Requested handler validates the exact SDK session and unique genuine ID, reserves a bounded FIFO entry, and awaits its permit. It returns to its wrapper only when it owns the sole active slot, phase `announced`. That slot stays owned across the genuine UI promise and SDK resolved event. Concurrent requested handlers cannot return early and reach their approve callbacks with another event's identity.
2. `approve` requires the gate live and active phase `announced`, then atomically changes it to `ui-entered`, captures **that record's actual toolCallId** and creates one ToolV1 permission request/original promise. No other callback may claim that slot. Publish exact once/deny options only, preserving session/call/request identity. Resolve only from that ToolV1 original response; no latest-call lookup during delivery.
3. Upon actual UI result, change active phase to `decision-returned` but do not release its slot. SDK's matching `tool_approval_resolved` completes/reclaims it and admits the next FIFO waiter. A resolved event for another/unknown/reused ID trips closed; a known terminal crossed event cannot release a newer active slot. If the SDK fails between requested and approve, matching resolved-false releases the `announced` entry without publishing a permission.
4. Explicit authorized ToolV1 interrupt/close first withdraws/rejects pending exact UI responders and clears waiting approvals, then invokes abort/disposal for that actual session. User/model-origin timeout/abort is a withdrawal/error, not invented human allow/deny. Force/pending takeover cancel is not sent to the adapter and cannot touch this gate or call abort/dispose. Do not automatically resubmit denied/aborted SDK tool calls.
5. Overflow, unexpected direct approve, missing/wrong identity, duplicate phase transition, handler timeout/error, protocol loss or disposal **synchronously sets a permanent closed/generation barrier before releasing/rejecting any waiter or callback**. Runtime error reporting is part of this barrier because runner emit otherwise swallows handler failure. Late handler continuations check the captured generation before acquiring/returning a permit. Reject pending approval promises (not successful deny decisions), withdraw published interactions with original IDs, reject all queued entries, and fail the original work/instance truthfully. Never reopen the gate or assign the next identity after this fault. Amux retains unknown outcomes and original resource charge until actual cleanup. Normal matching denial is not a fault and must let the next distinct approval proceed.

The SDK's generic handler budget is30s. A queued requested handler may time out while another human approval waits; preserve this as an explicit adapter failure/withdrawal, not an automatic approval, silent waiter release or reusable slot. No new shorter human-answer timeout is introduced. Runtime error callback must trip the barrier before SDK proceeds after its timed-out handler; verify that order offline. This is an SDK profile limitation, not an amux reacquisition/cancellation policy. Do not patch SDK timeouts or add an unreviewed retry.
